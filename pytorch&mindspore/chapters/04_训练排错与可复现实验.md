# 第 4 章　训练排错与可复现实验

loss 不下降、出现 NaN 或重载后结果改变，都不是一个统一的“框架有问题”。高效排错要沿数据到更新的路径缩小范围，每一步建立可证伪的判断。本章把项目 A 的验收拆成几个低成本实验，先证明计算正确，再扩大模型。

沿前几章的训练循环逐站检查：原始样本有没有读错，预测和标签的形状是否一致，损失只汇总了应训练的位置，反向后梯度是否有限，更新后参数是否变化。**可复现**在这里指记录足够的配置、数据版本和随机状态，让同一实验能被重新执行和比较；它不保证不同硬件上的每个浮点位都相同。

先故意在[短程序的形状实验](../短程序实验.md)里保留错误广播：程序仍会给出有限损失 $4/3$。若只看“没有异常”和“loss 是数字”，就会漏掉问题。把预测压成 `[3]` 后损失变成 0，这才定位到第一处错误。下面的排错顺序都遵循同一原则：每次提出一个可能原因，就运行一个能把它与其他原因区分开的小检查。

## 4.1 按信息流定位第一个异常

训练的数据流是原始样本、编码与标签、模型前向、损失、梯度、参数更新、独立评测。检查顺序也应沿这条路径。先打印少量实际样本及其标签，确认形状、dtype、数值范围与有效位置；随后只运行一个小批次，观察输出和 loss；最后检查参数是否收到有限梯度、一步更新是否改变了预期参数。

若语言模型所有位置都被 mask，损失归约分母可能为零；若 attention 某一行全是负无穷，softmax 可能产生 NaN。用更小学习率解决不了这些数据与目标问题。相反，有限但剧烈震荡的 loss 才可能提示学习率过大、梯度尺度不合适等优化因素。每个解释都要配一个能区分它与其他原因的检查。

## 4.2 三个最便宜的正确性实验

第一个是形状与梯度检查：用第 1 章的解析函数，对照手推、autograd 和中心差分。相对误差可定义为

$$
E=\frac{\|g_{AD}-g_{FD}\|_\infty}
{\max(1,\|g_{AD}\|_\infty,\|g_{FD}\|_\infty)},
$$

其中 $g_{AD}$ 是自动微分梯度，$g_{FD}$ 是有限差分梯度。绝对与相对误差一起看，避免梯度接近零时比例失真。

第二个是小样本过拟合：固定少量样本，暂时关闭不必要的正则化，用有足够表达能力的模型训练。若连这批样本都不能拟合，先检查标签、mask、梯度和更新。成功只说明模型能记住这批数据，不证明泛化；标签有冲突或模型表达受限时，也不应要求损失归零。

第三个是保存恢复：保存模型后在相同输入上重载，核对输出误差；再保存完整训练状态，中断后继续若干步，与不中断运行比较。前者检查推理恢复，后者检查训练恢复，它们不是同一个验收。

## 4.3 梯度诊断要记录有意义的量

设全体参数拼成向量 $\theta$，梯度为 $g$。梯度范数 $\|g\|_2$ 能显示尺度与突变，但数值大小依模型、损失归约和参数化而变，没有通用“正常范围”。还可记录相对参数变化 $\|\Delta\theta\|_2/(\|\theta\|_2+\varepsilon)$，其中小正数 $\varepsilon$ 防止除零。

```python
# PyTorch 2.7 调试片段；置于 backward 之后、step 之前。
for name, parameter in model.named_parameters():
    if parameter.requires_grad and parameter.grad is None:
        print("本轮未收到梯度:", name)
    if parameter.grad is not None:
        if not torch.isfinite(parameter.grad).all():
            raise RuntimeError(f"non-finite gradient: {name}")
```

`grad is None` 可能表示参数未参与这条路径，也可能是有意冻结或本批没有激活某分支，不能一概判为错误。梯度为零则表示计算得到零，这与没有梯度对象不同。先确定预期行为，再让诊断针对异常。

## 4.4 可复现不是只有一个 seed

至少记录代码版本、数据划分与处理规则、框架和设备版本、随机种子、超参数、检查点和完整命令。Python、NumPy、框架、DataLoader worker 都可能有各自随机源；GPU 某些操作还存在非确定性。PyTorch 官方明确指出不同版本、平台或设备之间不保证完全相同结果。[2.7 可复现说明](https://docs.pytorch.org/docs/2.7/notes/randomness.html)是行为边界，不应把“设了种子”写成跨机器逐位一致的承诺。

恢复训练通常还需优化器、学习率调度器、混合精度缩放器、随机数状态和数据读取位置。本册实验只用固定全批数据、CPU float64、单线程和带动量 SGD，所以状态相对简单；没有把这组简单条件的逐位恢复结论外推到多进程数据加载或 GPU 训练。

## 4.5 公平对照与资源记录

项目 A 先选一个变量，例如学习率或序列长度，其他配置尽量固定。序列变长同时改变每步 token 数和激活内存，比较时既报告训练步数，也报告有效 token 数与耗时。不要把更多训练预算带来的收益完全归因于模型改动。

GPU 操作可能异步执行，直接用 Python 墙钟包住一次调用可能只测到任务提交；测量时需按框架要求同步并先预热。峰值显存也应说明是否包含优化器首次初始化与验证。本册实际实验只使用 CPU，因此没有声称测过项目 A 的 GPU 吞吐；这些测量应在真实模型接入后完成。

验证集用于选超参数，测试集保留到阶段评估。总盯着测试结果调整配置，会让“未见数据”逐渐变成训练过程的一部分。最后保留普通结果和失败结果，写出观察到什么、猜测原因是什么、用哪个下一步检查区分解释。

## 4.6 深入：用对照区分原因，而不是罗列猜测

### 从第一个异常建立诊断树

先固定一条原始样本、token IDs、labels 与 mask，记录有效目标数；再固定权重做前向。若输入/标签错误，先修数据；若 logits 已非有限，逐层定位首次异常；若 logits 有限但 loss 非有限，检查全零分母、目标越界、log(0) 和归约；若 loss 有限但梯度异常，检查反向路径与精度；若梯度正常而参数不更新，检查 optimizer 的参数集合、lr、step 是否跳过和参数是否被重新创建。

不要一次改变多个条件。例如 NaN 仅在 AMP 开启时出现，可以先保持数据和权重不变切到 float32，再分别检查溢出、缩放与危险算子；两种精度都在同一全遮挡行出错，更支持 mask 边界问题。每次改变一个条件，才能解释检查支持或排除了什么。

### 小样本过拟合要有可识别的目标

选一条标签确定的短序列，重复同样输入和监督；固定初始化，暂去掉 dropout 与 weight decay，选择足够容量和合理学习率。记录逐 token loss，区别首 token 不确定性、EOS 错位和后续语法错误。若同一输入对应两个不同标签，就有不可消除的条件不确定性，不应把无法归零直接判为代码错误。

极小训练集拟合通过后，故意交换标签或移除因果 mask，查看检查是否能感知变动；但变化大小依赖权重和输入，需要多条可区分样本。随后恢复正规数据切分与正则化，检查验证。实现正确、优化成功和泛化是三项证据，不能彼此替代。

### 梯度裁剪的位置来自更新目标

全局范数裁剪定义为

$$
g_{clip}=g\min\left(1,\frac{c}{\|g\|_2}\right),\qquad c>0,
$$

零向量保持为零，实现可用稳定项避免除零。它改变更新方向的尺度；不修复标签、归约和 NaN。对于合批梯度应先累积、归一化和 unscale，再裁剪。逐微批裁剪通常不等价，因为范数运算不是线性映射。

取两个微批的**损失和梯度** $g_1=[10,0]$、$g_2=[-10,1]$，本例目标是两损失求和，阈值 c=1。合批梯度 `[0,1]` 裁剪后不变；逐微批分别裁剪后相加约为 `[0.004963,0.099504]`。尽管两者都经过“clip”，最后的更新不是同一个算法。

### 记录能重建事件的日志

一行诊断至少关联 `run_id, global_step, batch_id, valid_tokens, loss_sum, loss_mean, grad_norm, lr, update_skipped`。在线 RL 还需 `policy_version, rollout_id, reward_status, completion_tokens`。把异常批次的最小可复现输入与配置保留下来，才能区分“本次坏数据”和“某个版本稳定出错”。不要只保留最后一张曲线。

性能排查同样需要分段：数据准备、传输、前向、反向、更新、评测。若每步数据 1 秒、GPU 计算 0.3 秒且不重叠，即使计算优化到 0.15 秒，总时间也只从 1.3 秒降至 1.15 秒。先测占比，避免在小头上做大优化；有异步重叠时需测真实关键路径，而非直接相加各段墙钟。

## 4.7 本册验收与完整问答

### 题 1：eval、no_grad 与 detach 分别控制什么？

**题目：**PyTorch 模型含 Dropout 与可训练 Linear 参数。调用 `model.eval()` 后，在默认梯度模式下执行前向，输出仍有 `grad_fn`。请说明是否异常；验证时应怎样处理；`prediction.detach()` 又改变什么？

**参考答案：**`eval()` 切换模块的训练行为，例如关闭 Dropout 的随机丢弃，不关闭求导记录，输出有 `grad_fn` 并不异常。验证通常用 `model.eval()` 配合 `torch.no_grad()`。`detach()` 返回与原求导历史断开的张量，适合保存预测或日志；把它放在训练损失关键路径上会切断该路径的梯度。

**面试追问：**为什么收集每步 loss 的列表可能让显存持续上升？

**追问回答：**若保存带图张量，可能延长相关计算图或保存张量的生命周期。日志通常保存 `loss.item()` 等普通数值；需要继续求导的数据才保留求导联系。

### 题 2：梯度突然放大 32 倍，怎样排查？

**题目：**固定同一组 $B=32$ 条样本、模型参数和各样本损失，原代码用 $L_1=\sum_i\ell_i/32$，新代码误用 $L_2=\sum_i\ell_i$。不含其他损失。请说明梯度关系，并给出真实训练里发现约 32 倍梯度变化时的排查顺序。

**参考答案：**本题精确有 $\nabla L_2=32\nabla L_1$。先比较 loss 的 sum/mean、有效样本或 token 分母与累积权重，再看数据、奖励尺度、混合精度缩放与异常值。实际 batch 内样本变化时，不能仅由大小 32 推断梯度恰好放大 32 倍。

**面试追问：**直接加大梯度裁剪能解决根因吗？

**追问回答：**裁剪可限制梯度范数，但会掩盖错误归约，且改变优化行为。应先修正损失定义，再按原目标选择合适裁剪阈值。

### 题 3：模型重载一致，继续训练却偏离，如何定位？

**题目：**一个带动量、学习率调度和随机打乱数据的训练，在第 40 步保存了模型参数。重载后，固定输入的 eval 输出与原模型一致，但第 41 步参数不同。请列出应比较的训练状态，并设计一个能区分“前向重载成功”与“训练恢复成功”的检查。

**参考答案：**先比较下一批样本是否相同、优化器动量与步数、调度器学习率、随机数状态、混合精度缩放状态。建立两条分支：原训练连续做第 41 步；另一条从完整检查点恢复后做同一批数据的第 41 步，比较 loss、梯度与参数。前向一致验证当前模型，下一步一致才覆盖恢复状态。

**面试追问：**固定 seed 足以保证所有设备完全相同吗？

**追问回答：**不够。算子、并行归约、设备与版本也会影响结果。应记录环境和确定性设置，用适当容差比较数值，并说明验证范围。

### 题 4：小数据不降 loss，怎样用最小检查定位？

**题目：**一个语言模型对一条固定短序列重复训练，loss 保持不变。无 Dropout，输入/标签只移位一次，但你还没检查有效 mask、梯度和 optimizer 参数集合。请按数据→前向→反向→更新设计检查，说明每一步的可证伪结果；不能只回答“调学习率”。

**参考答案：**先打印有效目标并确认数量>0，检查复制/错位标签；固定模型检查每位置 logits 和 loss 是否有限；反向后找预期参与层的梯度是否存在且有限；核对 optimizer 包含这些参数且 lr>0；保存更新前后参数差，并检查 step 是否因溢出跳过。无参数变化先查更新路径；有变化但目标不改善再考虑容量、曲率与学习率。提交一张逐站输出表和能重现失败的最小脚本。

**面试追问：**某个参数 grad=None 就一定是 bug 吗？

**追问回答：**它可能被有意冻结或本批未使用。先确定预期计算路径；grad=None、grad 为零、有限非零梯度是不同状态。

### 题 5：逐微批裁剪与合批裁剪为什么不同？

**题目：**两个微批的损失和梯度分别为 `[10,0]`、`[-10,1]`。目标是两损失求和，不取均值；范数裁剪阈值为 1。比较先加梯度再裁剪，与分别裁剪再相加的最终梯度，解释对梯度累积的影响。

**参考答案：**合批梯度 `[0,1]`，范数 1，不变。逐批结果 `[1,0]` 与 `[-10/√101,1/√101]`，和约 `[0.004963,0.099504]`。范数裁剪非线性，改变执行次序会改变更新；应该按目标完成累积与归一化后，再裁剪合批梯度。

**面试追问：**AMP 的放大梯度能直接用同一阈值裁剪吗？

**追问回答：**不应如此。先 unscale 恢复原梯度尺度，否则阈值对应了另一个数量级；同时遵守累积窗口与更新跳过规则。

### 题 6：算子快两倍，为何训练只快一点？

**题目：**固定质量、数据和设备，每步数据准备耗时 1 秒、GPU 计算 0.3 秒，二者完全串行。优化后只有 GPU 计算降至 0.15 秒，其他不变。计算端到端加速比；若要继续优化，说明下一步测什么，不能直接假定需要更强 GPU。

**参考答案：**原步耗时 1.3 秒，新步 1.15 秒，加速比约 1.130435。先测数据读取、解码、预处理、CPU 负载和传输是否可重叠，确认瓶颈；如果有异步重叠，重新测关键路径与有效 token/s，不能沿用串行相加模型。

**面试追问：**只用 GPU 利用率判断训练瓶颈够吗？

**追问回答：**利用率是提示，需要 profiler、分段耗时、batch/长度和同步协议进一步支持；高利用率不等于算力效率高，低利用率也可能来自等待和工作负载太小。
