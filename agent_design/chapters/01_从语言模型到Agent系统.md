# 第 1 章：从语言模型到 Agent 系统

> 目标：先讲清组成、数据流与控制边界，再决定使用什么模型。前置：[语言模型的条件分布](../../post_train/chapters/01_语言模型到后训练.md)。

## 1.1 多了一次模型调用，不一定多了一个 Agent

普通问答把输入映射为输出。任务系统还可能在中途读取文件、查询工具、检查结果，再决定下一步。这里把 Agent 定义为：围绕目标，根据当前可见信息选择动作，并利用动作反馈继续决策的系统。固定流水线也能完成复杂工作；只有任务确实需要依反馈分支时，动态决策才提供额外价值。

先看本地计算例子：“求 $(7+5)/3$ 并说明计算依据。”系统可以先调用加法工具获得 12，再把 12 作为除法输入，最后输出 4。模型负责提出动作，执行器负责校验并调用函数，观察负责返回真实结果。模型写了“已得到 12”，并不能替代工具实际返回 12 的证据。

## 1.2 五个组件与一次闭环

| 组件 | 输入与输出 | 需要明确的边界 |
| --- | --- | --- |
| 任务定义 | 目标、约束、成功标准 | 什么算完成，允许调用哪些工具 |
| 状态管理 | 历史、证据、进度 → 当前状态 | 哪些信息可靠，哪些仅为猜测 |
| 决策策略 | 当前状态 → 动作或结束 | 可以是规则、语言模型或二者组合 |
| 执行器 | 合法工具请求 → 返回值或错误 | 参数校验、权限、调用预算 |
| 评估与停止 | 结果、预算、错误 → 继续或终止 | 不把“模型宣布完成”直接当成功 |

```mermaid
flowchart LR
    A[目标与初始状态] --> B[决策策略]
    B --> C[请求校验]
    C --> D[工具执行]
    D --> E[观察与状态更新]
    E --> B
    E --> F[完成检查或预算终止]
```

日志至少记录请求 ID、工具名、参数、观察、错误类别和停止原因。它们是系统事件，不要求保存模型私有的内部推理。面向使用者的简短理由可以帮助复核，但可读理由不保证反映真实决策机制。

## 1.3 状态不等于聊天记录

回到算术例子：加法工具真实算出 12 是环境中的事实；控制器收到的“成功，结果 12”是观察；模型随后请求 `divide(12,3)` 是动作。令第 $t$ 步外部真实情况为 $z_t$，系统看到的观察为 $o_t$，模型选择的动作为 $a_t$。按时间排列的可见观察和动作叫历史，记为 $h_t=(o_0,a_0,o_1,\ldots,o_t)$。系统通常看不到全部 $z_t$，只能依据这份历史决策。可写作

$$
a_t\sim\pi_\theta(\cdot\mid h_t),\qquad
o_{t+1}\sim P(\cdot\mid z_t,a_t).
$$

式中 $\pi_\theta$ 是参数为 $\theta$ 的决策策略，$P$ 是环境产生观察的概率规则。实际实现常把历史用函数 $f$ 压缩为结构化状态 $s_t=f(h_t)$，例如已确认事实、待查问题、最近工具结果、剩余预算。压缩可能丢失信息，因此 $s_t$ 未必满足马尔可夫性，即“给定当前状态与动作，就足以预测下一步”的条件；不能只因变量叫 `state` 就套用完整可观测 MDP 定理。形式化背景见 [RL 的状态与转移](../../RL/chapters/01_MDP与回报.md)。

例如工具返回“除数不可为零”，应记录这是参数错误；若返回“服务暂时不可用”，应记录暂时故障。两者表面上都是失败，却需要不同转移：前者修改请求或结束，后者可能有限重试。完整日志与供模型阅读的摘要最好分开，以便检查摘要是否遗漏关键约束。

## 1.4 ReAct 提供的思路与边界

ReAct 将任务推理、动作和环境观察交替组织，是理解闭环交互的经典案例。其核心提示实验使用冻结模型，不是每次调用工具都进行 RL 更新。[原论文第 2 节](https://arxiv.org/html/2210.03629v3)

教学实现可以借用闭环，而不强制每个工具前都生成长篇思考。简单算术适合确定性流程；信息不足时才检索；观察与原计划冲突时才重规划。让系统多说几段话会消耗预算，也可能强化错误假设，收益需要对照实验确认。

## 1.5 系统运行与策略训练分开

一次 Agent 运行更新的是上下文、缓存与任务状态；SFT 或 RL 更新的是模型参数。保留失败摘要后重试，可以改变条件输入，却不意味着权重已经学习。反过来，用 RL 训练过的模型也可以在部署时执行固定流程。

若要训练工具策略，需要先定义轨迹中哪些 token 是模型动作、哪些是工具观察，再定义奖励、终止和预算。把工具观察也当成策略自行生成的动作计算 log-prob，会改变训练目标。相关训练基础见 [后训练中的 RL 数据流](../../post_train/chapters/05_RLHF与PPO训练系统.md)。

## 1.6 深入：事件重放、状态不变量与执行确认

把状态更新写成纯函数 `reduce(state,event)->new_state`：初始状态和有序事件可以重建任务，实际工具执行只在在线执行器发生。事件至少包括 task_id、logical_request_id、attempt、tool、arguments、status、result、budget_delta、evidence_id 和停止原因。完整事件与供模型读取的摘要分别保存，重放不重新发出写操作。

应验证三个不变量：实际调用数单调且不超过预算；只有匹配请求的成功观察才能更新对应结果；completed要求外部判据而非模型宣称。校验拒绝是否计入调用预算由契约定义，不能在日志里一会儿算一会儿不算。状态转换失败时保留最早错误，中间值不冒充最终答案。

执行超时需要三态：确认未执行、确认执行、执行结果未知。带副作用请求的未知状态不能简单重复；使用幂等键或查询结果确认，保证同一逻辑请求不会被视为多个新操作。幂等不等于网络端“恰好一次”：可重复传输，但服务端根据键去重；服务不支持时需要明确补偿/人工处理边界。

模型提出动作、校验动作、环境执行、确认完成分别验收。确定性控制器只证明控制流；接入模型后再测试动作选择与适应反馈，不能把脚本的正确路线直接标为通用规划能力。运行日志提供行为证据，文字理由不自动证明因果机制。

## 1.7 完整自测与面试问答

### 题 1：Agent、工作流与工具调用有什么区别？

**题目：**任务是计算 (7+5)/3。只允许 add(left,right) 与 divide(numerator,denominator) 两个工具，每次返回本次请求的成功标记和数值；工具均成功，调用预算为 2。请列出初始记录、两次请求和观察、最终检查；说明这条确定性路线能否证明系统已学会自主规划。

**参考答案：**初始记录包含任务、预算 2、空观察和未完成标记。先请求 add(7,5)，收到成功且值 12，剩余预算 1；再请求 divide(12,3)，收到成功且值 4，剩余预算 0。核对请求归属、运算和目标后才标记完成并返回 4。这是有工具与观察的闭环执行；固定路线本身不足以证明通用规划能力。

**面试追问：**Agent 一定每一步都要调用大模型吗？

**追问回答：**不一定。系统可把部分步骤交给确定性代码；自主决策程度要看它在哪些位置依据观察选择或调整动作，不能由模型调用次数判断。

### 题 2：失败记录与预算为什么属于任务状态？

**题目：**检索服务在某任务中持续返回 temporary_unavailable，表示暂时不可用。控制器最多允许 3 次实际调用，同一请求可以重试。一个实现删掉失败观察并把已用调用数重置为零，另一个保留错误类型、请求标识和调用数。请给出各自的风险与第二个实现的停止规则。

**参考答案：**重置计数使预算失去约束，控制器可能持续重复请求；删掉失败原因还会妨碍区分无结果、权限与服务故障。正确实现每次实际调用都计费，失败也累计，最多第三次失败后以预算耗尽停止。允许重试不等于重置预算，失败也应进入日志。

**面试追问：**重试会产生重复写入时怎么办？

**追问回答：**读取与写入需要分别设计。带副作用操作应使用请求标识、幂等机制或执行结果核验；超时表示未拿到确认，不必然表示操作未执行。

### 题 3：怎样判断多 Agent 是否值得增加？

**题目：**一项文献核查任务需要查证两条互相独立的事实，最终汇总必须给出来源。可用方案 A：一个 Agent 顺序查；方案 B：两个 Agent 各查一条后合并。每题总模型输出上限 2000 token、工具调用上限 6，合并消耗也计入。请设计公平比较，并说明何时 B 有可能更合适。

**参考答案：**固定同一任务集、模型和工具；两方案使用相同总预算，记录事实准确率、来源正确率、端到端耗时、实际 token 和工具数。B 在两条查证能独立执行、并行节省等待、合并规则明确且额外成本可控时值得尝试；须检查互相抄错和合并遗漏，收益由结果确认。

**面试追问：**两个 Agent 给出相同答案就是相互验证吗？

**追问回答：**未必。同模型、同提示、同检索可能共享错误。应核对独立证据和可执行判据，并记录分歧如何解决。

### 题 4：手写可重放的状态 reducer

**题目：**定义算术任务的event schema和纯reducer，实现重放成功、错误请求归属、暂时失败重试与预算耗尽四条轨迹。重放不得实际调用工具，提交状态不变量和最终值。

**参考答案：**事件带任务/请求/attempt/实际执行与结果，reducer只更新匹配证据和预算；成功路线得到4，错归属不接受结果，失败累计实际调用，耗尽以明确原因停止。中间12不成为除法最终答案，在线执行器与重放分离。

**面试追问：**日志事件乱序怎么办？

**追问回答：**依序号和因果ID重建，缺事件或重复事件要显式处理；不能按收到顺序无条件覆盖状态。

### 题 5：超时重试的执行语义

**题目：**一个写工具超时，服务端可能已完成。设计logical_request_id、attempt、幂等键与结果确认流程；给出没有服务端幂等支持的限制。

**参考答案：**同一逻辑操作重试沿用幂等键，各传输attempt分开记录，先查已有执行结果，再按服务契约重试。未知不等于未执行；无去重/确认能力时无法保证无重复副作用，应停止自动重复并保留待处理状态。

**面试追问：**只在客户端缓存结果能避免所有重复吗？

**追问回答：**首次超时可能未取得结果，客户端崩溃也可能丢记录；需持久化与服务端契约共同保证。

### 题 6：固定工作流与动态控制的最小比较

**题目：**为算术成功、工具临时故障和参数无效三个场景定义固定工作流与动态恢复策略，匹配工具/token预算。提交逐事件轨迹和质量/成本表，说明何种证据支持动态决策收益。

**参考答案：**正常任务看正确与额外成本，故障任务看是否按反馈有限恢复，参数错误看是否修正或正确停止。使用同工具与预算、固定故障注入，比较端到端而非调用数；脚本通过只支持控制逻辑，模型决策需独立运行。

**面试追问：**允许动态恢复但故障不可重放能归因吗？

**追问回答：**需保存故障快照、配对控制或明确不可比边界，不能把外部服务差异归为策略收益。
