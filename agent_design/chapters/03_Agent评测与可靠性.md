# 第 3 章：Agent 评测与可靠性

> 目标：把好看的演示变成可复核的实验，区分模型决策、工具执行和任务结果。

前两章已经定义动作、观察、请求校验和失败恢复。现在把“系统会算 $(7+5)/3$”变成可测结论：题目是否算对，是否确实调用过工具，遇到暂时故障时是否在预算内恢复？**评测协议**是运行前约定的题目、预算、成功判据和记录方式；同一协议下的结果才方便比较。

## 3.1 成功需要外部定义

模型输出“已完成”只是一个事件。对算术任务，成功可定义为最终数值正确且证据链可追溯；对检索问答，还要检查引用确实支持主张；对文件操作，则需核对目标文件的实际状态。先写成功判据，再运行系统，否则容易在看到输出后降低验收要求。

将一次任务的观测记为 $\tau=(s_0,a_0,o_1,\ldots,a_{T-1},o_T)$，定义外部评估 $g(\tau)\in\{0,1\}$，测试集上成功率为 $N^{-1}\sum_i g(\tau_i)$。若评估本身由语言模型完成，应抽样人工复核，并记录评判模型、提示、候选顺序及一致性。评判器输出不天然是真值。

## 3.2 同时报告质量、成本和失败原因

| 维度 | 可记录指标 | 容易误读之处 |
| --- | --- | --- |
| 结果质量 | 成功率、事实/格式正确率 | “调用成功”不等于任务成功 |
| 工具使用 | 有效请求比例、冗余调用、恢复率 | 调用越多不代表做得越充分 |
| 成本 | 模型 token、工具次数、耗时 | 只比较次数会遗漏单次调用差异 |
| 停止行为 | 提前宣布完成、预算耗尽、重复循环 | 只统计成功样本会隐藏困难任务 |

对有限预算 $B$，可比较 $S(B)=P(\text{预算内完成})$，而不仅给一个最高分。更复杂系统若只在十倍调用下提高一点成功率，仍可能对某些任务有价值，但应明确成本。重复同一道题多次取最佳结果，还需要说明如何选择最佳；知道测试答案才能选择的上界，不等同于部署系统实际成功率。

## 3.3 建立能定位问题的轨迹

最小日志保存任务 ID、模型与工具版本、每次请求和观察、重试次数、预算变化及停止原因。原始证据与摘要分开保存，错误用结构化类型，不用一段无法统计的“出现问题”。运行含随机采样时记录生成参数与种子；外部服务不可重放时保存当时可公开的返回快照并说明限制。

失败可按最早可确认原因分类：目标理解错误、计划依赖错误、参数不合法、工具故障、证据误读、记忆污染、错误验证、停止条件错误。一个任务可能有多个问题，但先定位最早错误通常更利于修复。仅用最终回答让模型猜失败原因，容易生成看似合理却无日志支持的故事。

## 3.4 从单例到对照实验

先建立小而多样的用例：直接成功、空检索、工具暂时失败、参数错误、相互矛盾证据、重复响应、预算不足。它们检查控制逻辑。随后加入未参与开发的真实任务，评估模型是否能正确选择动作。二者分开报告，不能拿规则脚本通过测试来宣称 LLM Agent 达到某准确率。

在同一题集上比较基线时，固定模型、工具集合、提示信息与预算；每次仅改变一个机制，例如有无失败摘要。对每题保留两个系统的结果，做配对差异；随机生成需要独立重复。若更换模型又增加工具，无法把收益归因于规划策略。统计原则可参照 [推理评测与实验设计](../../post_train/chapters/07_推理评测_蒸馏与实验设计.md)。

## 3.5 两篇经典论文教什么判断

ReAct 的实验不支持“加入推理与工具必然提升所有任务”；Reflexion 的某些代码任务也出现下降。具体数值、模型和反馈预算见 [ReAct 阅读卡](../papers/notes/2022_ReAct.md) 与 [Reflexion 阅读卡](../papers/notes/2023_Reflexion.md)。学习价值在于观察它们如何构造对照，以及哪些机制依赖评估反馈质量。

真实系统中的重试还会改变信息条件。如果第一轮可看到测试反馈，第二轮就不再是无反馈的一次作答。报告单次提交结果时，必须同时披露此前的生成、测试与修订预算，避免把试错收益写成模型自身的一次生成能力。

## 3.6 与后训练项目连接

若准备把成功轨迹用于 SFT，应保留失败轨迹供分析，按任务而非单条步骤划分训练测试，避免相同题目的动作历史泄漏。若准备用 RL 优化工具调用，应先稳定环境、奖励和日志，区分工具观察与策略动作，统计奖励漏洞。[RLVR 的验证器边界](../../post_train/chapters/06_GRPO与RLVR.md) 同样适用。

一个合格的小项目交付应包含：接口说明、固定任务集、可运行控制器、结果表及失败轨迹。模型选择、训练与系统编排可以依次改进；一次把所有环节复杂化，会让负结果难以解释。

## 3.7 深入：故障注入、选择偏差与可交付报告

正常运行、参数错误、重复响应、超时、空结果与矛盾证据分别建立固定用例。故障注入保存同一观察快照，比较两个控制器时不让服务波动成为隐藏变量。离线重放验证控制逻辑，在线模型调用验证动作选择，两种样本与结论分开标记。

失败定位按最早可证实偏离判据的事件，同时保留后续影响。只在成功轨迹上平均成本会遗漏失败的大量重试；总体成本包含所有任务。例：10题，8题成功各2调用，2题失败各6调用，成功子集均值2，总体均值(16+12)/10=2.8。

恢复率的分母也需明确：能恢复的预定义故障集合、全部接口失败还是全部任务失败。系统遇到难题更频繁调用工具时，正常工具子集不是随机样本，不能把条件成功率外推到所有题。可以用同题固定故障/正常返回做配对干预，检查策略是否正确处理反馈。

模型评判器要交换候选顺序、隐藏方法标识并用人工/可执行真值抽查，报告分歧。通过增加重试、更多候选或反馈得到的最终成功与无反馈一次结果分开；选择规则本身是系统的一部分。报告包含任务契约、版本、全量逐题结果、预算、不确定性与可定位失败，不能只展示最漂亮轨迹。

## 3.8 完整自测与面试问答

### 题 1：工具调用成功率高，任务成功率为何仍低？

**题目：**100 个任务各有多次工具调用。所有实际调用中 99% 返回 ok=true，但只有 40 个任务通过独立答案验证器。ok=true 只表示接口执行成功，不保证参数对应正确问题。请给出排查顺序、需要保存的证据及为什么不能只升级工具服务。

**参考答案：**先抽取失败轨迹，核对参数语义与请求归属，再看返回证据是否相关、模型是否使用证据、是否提前结束、最终验证是否与任务一致。保存任务标识、请求、观察、时间、预算与最终判据，分别统计接口失败、选错工具、查询错误、证据误用和答案错误。99% 与 40% 的分母不同，无法直接推断只靠修好余下 1% 调用能解决任务失败。

**面试追问：**每步 99% 成功，十步全部成功约多少？

**追问回答：**仅在各步独立、都必需且单步成功概率相同的假设下，为 $0.99^{10}\approx0.9044$。实际调用相关、长度不同，需要直接测端到端成功率。

### 题 2：Reflexion 风格的记忆如何公平评测？

**题目：**方案 A 允许最多 3 次作答，每次看到验证反馈，并把失败摘要带入下一次；方案 B 只作答 1 次且无反馈。观察 A 成功率更高。请说明该比较能否把收益归因于记忆，并设计至少两个补充对照。

**参考答案：**不能单独归因于记忆，因为尝试数、反馈和输入都改变了。补充“3 次尝试、同反馈、无跨次摘要”的对照，以及“3 次尝试、同反馈、带摘要”的方案；可再比较等长但无有效信息的摘要。固定总生成与测试预算、最终答案选择规则，报告每次及最终成功率。

**面试追问：**把失败摘要加入输入等于更新模型权重吗？

**追问回答：**不等于。它改变条件上下文；只有执行训练并修改参数，才发生权重更新。报告中需区分上下文适应与参数学习。

### 题 3：怎样预先写出状态机的失败判据？

**题目：**固定控制器计算 (7+5)/d，先调用 add 再 divide；成功标记需两步都通过。最大实际调用数为 3，d=0，add 返回成功且值 12，divide 的本地校验禁止分母为零，校验拒绝不计实际调用。请在运行前写出状态、调用数、最终值与错误类别的预期。

**参考答案：**加法消耗 1 次调用，得到 12；除法在执行前以 division_by_zero 拒绝，终态为 failed，实际调用数 1，最终值为空。12 只能作为中间观察保留，不能作为任务最终答案。验收同时检查错误类型和没有执行非法除法，而非仅看程序是否退出。

**面试追问：**如果一次暂时故障后重试，两次请求标识应怎样设计？

**追问回答：**同一逻辑操作的重试可保留逻辑请求标识，并另记尝试序号；成功后进入下一操作。这样日志能区分重复尝试与新的任务步骤。

### 题 4：修复成本统计的选择偏差

**题目：**使用8成功×2调用、2失败×6调用的10题数据，算两种平均成本，定义成功率—预算曲线；说明提前放弃难题怎样影响指标。

**参考答案：**成功子集均值2，总体2.8，成功率.8。预算曲线每点对全部同题按统一停止规则统计；提前放弃可降成本也降低质量，要按难度和配对失败检查，不能只给成功样本的省钱结论。

**面试追问：**失败没有最终答案就可以删掉吗？

**追问回答：**必须保留为失败与已发生成本，否则分母和资源被有利地选择。

### 题 5：设计可重放故障评测

**题目：**为状态机编写正常、临时失败、重复成功响应、错误请求归属、预算不足五类轨迹，预先写最终状态和调用数。接入模型时哪些部分还需单独测？

**参考答案：**固定事件与契约验收reducer不变量，重复响应不重复覆盖/计成功，错误ID不接受，预算不足正常失败。模型还需测试合法动作选择、参数语义与停止判断，脚本用例通过只验证控制层。

**面试追问：**故障只挑最容易恢复的算有效恢复率吗？

**追问回答：**它只支持该故障子集，需明确覆盖并补困难/不可恢复类别，不能外推全系统。

### 题 6：Agent 项目的面试答辩

**题目：**提交接口、控制器、至少三类失败、固定任务集和同预算基线。用一条失败日志讲清最早错误、修复假设、单因素验证和剩余局限。

**参考答案：**结论对应真实事件与外部判据，修复对照控制模型/工具/预算，记录正常任务的额外成本。区分控制规则、模型适应与参数训练；没有运行的能力明确留为设计，不能把通用框架名称当实现证据。

**面试追问：**项目新意可以只是多个组件拼接吗？

**追问回答：**拼接可证明工程能力；研究贡献还需一个明确缺口、受控实验和能区分解释的证据。
